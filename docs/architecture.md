# Application structure

Deerstalker starts as one macOS 14+ Swift package executable, using SwiftUI for document windows and PDFKit for the initial PDF reader. There are no external package dependencies. This is an implementation baseline to evaluate, not a demonstrated memory advantage over Acrobat.

| Area | Responsibility | Initial status |
| --- | --- | --- |
| `Sources/Deerstalker/App` | Application scene and window defaults | One Home/Search/reader window with an explicit ReadingSession |
| `Sources/Deerstalker/Home` | Home, recent documents and creation tools | Convert/Compress/Combine implemented in source |
| `Sources/Deerstalker/Convert` | Mixed-file conversion and per-file previews/outputs | ImageIO, bounded OOXML import, OMML/page furniture/inline artwork and native Word/TextKit layout, local HTML/MathML/WebKit Markdown output |
| `Sources/Deerstalker/Assistant` | Reusable on-device Ask | Generic passages/locations, citation validation and a caller-owned navigation closure; no Search/PDFKit dependency |
| `Sources/Deerstalker/Search` | Persistent local library index and ranked page results | PDF/Markdown FTS5 actor, previews, manual refresh and on-device query planning, previews and saved highlights |
| `Sources/Deerstalker/Documents` | File decoding, save representation and content routing | UTF-8 Markdown/plain text and committed PDF bytes |
| `Sources/Deerstalker/PDF` | Document session, reading controls, search and notes | PDFKit adapter, cancellable search, comment navigation and note transactions |
| `Sources/Deerstalker/Markdown` | Reading, editing and source/preview split | Shared source binding and mode controls |

## Document ownership

ReadingSession owns the canonical document value inside the main window, replacing the separate DocumentGroup scene. Home and search use the same open route; file bytes load on a utility task before the content transition. Save writes atomically after checking the original bytes against disk, and Save a Copy provides conflict recovery. Leaving a dirty document, closing the window or quitting asks whether to save. Markdown reading and editing consume that same source. Switching mode changes the presentation without creating a second editable copy. PDF note transactions serialise changes and commit the resulting bytes to that same document value; opening and reading alone preserve the original bytes. The writer rejects cross-format saving instead of disguising text as PDF or PDF as Markdown. The packaging script declares PDF and Markdown file associations. Home creates new files for image conversion and combining.

The PDF session owns one PDFDocument per open workspace and preserves it across unrelated view updates so that selection, zoom and page position are not reset. It retains original Data and PDFKit's parsed representation. The source includes previous/next page, page count, zoom, fit page, load-error UI and password entry. Password input is cleared after an unlock attempt. Large-file loading, reopen/revert behaviour, rendering caches and memory after closing still require evaluation; this baseline makes no low-memory guarantee.

Document search uses PDFKit's asynchronous text search after a 250 ms input delay, with case sensitivity, line context and page links. Replacing a query cancels prior work, clears results and invalidates its callback generation. At most 500 result objects are retained; further matches cancel the search and show a refinement prompt. This cap bounds the application's result list, not PDFKit's internal allocations. Command-F opens the search panel and focuses its field. Home has a separate cross-document lexical index; this in-document search remains independent. No OCR, semantic runtime or proprietary PDF Search PRO formula is implemented.

The comments panel loads non-empty annotation contents only when opened, skips popup/form-widget duplicates, and yields between pages. It displays author, date, page and content as cards. Clicking a card navigates to the annotation; the PDF annotation-hit notification selects its card. Closing the workspace cancels search/comment work. The Add Note command captures a location near the current text selection or on the current page and opens a composer. Its draft survives sidebar switches; a second Add Note action does not replace an unfinished draft. Author is optional and defaults to Me, without reading the system account name. Selection text in the composer is contextual only: the saved annotation is a page note, not a text-range highlight.

`PDFNotes` adds or removes the standard Text annotation and serialises the document, rolling the annotation action back if serialisation fails. The session registers inverse annotation actions with the window undo manager instead of retaining a full PDF snapshot for every undo. Successful commits update the document binding without reloading the live PDF; the document scene still owns saving to disk. Encrypted or restricted documents cannot be edited through this path. This avoids silently dropping encryption on rewrite. Offscreen session tests verify document writeback, retained PDF identity, note/reply undo and redo, and draft retention. Actual document-window dirty tracking, autosave and menu interaction still need live verification.

Replies now retain their actual parent and are grouped below the original comment. A Reply action captures that comment as the draft's parent, including nested replies. Starting another reply does not overwrite an unfinished draft. Editing/deleting existing notes, resolution, richer anchor previews and full document-window UX remain pending. Annotation selection, scrolling, password unlocking and notification delivery still require live verification.

## Reply persistence

PDFKit rejects a PDFAnnotation object as the IRT value. Supplying a dictionary is accepted, but writes a separate copy rather than a reference to the parent annotation in the page's Annots array. PDFKit also drops NM identifiers in the tested rewrite. Those results are not sufficient for interoperable threads. The [Adobe PDF reference](https://opensource.adobe.com/dc-acrobat-sdk-docs/pdfstandards/pdfreference1.6.pdf) defines IRT as the annotation being replied to and requires both annotations on the same page; [Apple's setter contract](https://developer.apple.com/documentation/pdfkit/pdfannotation/setvalue(_:forannotationkey:)) reports assignment success, not a guarantee of preserved relationship identity.

`PDFCommentGraph` imports standard relationships through CoreGraphics dictionary identity and retains names and parent links independently of PDFKit. It maps the complete PDFKit rewrite back to live annotations, checking page order, subtype, rectangle and content. `PDFReplyWriter` then appends updated annotation objects with standard NM, IRT and RT entries, pointing to the actual parent object in the page. The file uses standard PDF incremental xref/trailer updates; there is no private-only thread store and no new application dependency.

The bounded writer accepts only a complete unencrypted classic-xref PDFKit rewrite, without Prev/XRefStm in that rewrite. It reads object dictionaries by xref offsets and never searches content streams for replacements. Unsupported structures, unknown parent relationships, Group relationships, cycles, missing parents and cross-page parents prevent a commit. It is not a general PDF parser/editor. Incoming documents can use other layouts because CoreGraphics reads them and PDFKit produces the intermediate rewrite; if that output is outside the supported profile, editing is refused. Existing unsupported relationships are not silently discarded.

Controlled tests preserve nested/sibling relationships across repeated saves, reopen and undo/redo; independently generated pypdf input also retains its Unicode NM name and parent links when a new reply is added. Independent pypdf inspection confirms each IRT is an indirect reference to the actual same-page parent in Annots. Acrobat 26.002.22031 visibly grouped the root and all three replies into one conversation in the tested fixture. PDF Expert subsequently opened the same fixture through Finder's Open With menu: its annotation list showed two top-level items and its note popup showed the root only, without the three replies. Do not claim matching conversation presentation in PDF Expert; its behaviour reinforces the need for an explicit conversation inspector in Deerstalker. Screenshots are retained under the threading evidence directory. This is version- and fixture-specific compatibility evidence, not a guarantee for every PDF/viewer.

The Markdown preview uses Foundation's Markdown parser and its presentation intents to group styled runs into paragraphs, headings, lists, quotes and code blocks. SwiftUI provides native block layout, readable line width and selectable text; code blocks scroll horizontally. Preview updates coalesce typing for 150 ms. This is not a complete document renderer: tables, images, mathematics, code highlighting and relative assets remain pending. Parsing still occurs on the main actor, so large-file responsiveness remains unmeasured. The source editor and split layout are present in source, but have not been exercised in a running app. Undo grouping, save/revert, external changes and selection across mode changes remain validation work.

## Next feature boundaries

Keep PDF annotations attached to the document, with stable annotation identity, page/geometry anchors and reply relationships. A conversation inspector should select the same annotation as the page view. Implement standard PDF reading/writing and round-trip checks before presenting comments as interoperable. No sample conversation or placeholder storage is installed in the scaffold.

Deerstalker is independent of Baker. The equation-region tool, cross-app request/result handling and Baker settings have been removed at the user's request. Standard PDF selection/copy remains native PDFKit behaviour. Baker separately exposes an app-neutral recognition adapter for possible future clients; Deerstalker does not call it.

The shared ReaderZoom model observes native PDF scale changes, applies whole-page/width fitting and updates WebKit page zoom for search Markdown. Native Markdown reading/editor text scales through font sizes, keeping layout and text selection intact. Visible controls expose −, percentage presets, + and Fit, with keyboard equivalents. General settings retain appearance and default Markdown zoom; Ask retains response detail and local conversation history controls.

For optional folder-wide semantic retrieval, see [local search and model choices](search-models.md). Hugging Face model downloads and inference are planned, not implemented; the first candidate is Qwen3-Embedding-0.6B MLX 4-bit. An idle reader should not load an embedding model.

The user approved Home and folder indexing on 19 October. The implemented local search is described in [Home and local search](home-and-search.md); it uses the system SQLite3 module without a package dependency. The Baker connection has been removed. Sync remains outside the reader path. Ask, Explore and indexing use only local processing. No cloud inference path is present.

## Library search in the main window

The Home Search action and Command-Shift-F switch the existing Home window to Search. Command-Shift-H and the Home button return to Home; query and result state remain in HomeModel. HomeModel coordinates the persistent LibraryIndex actor, grouped page results, filtering and bounded Previous/Next navigation. SearchPDFModel owns a cancellable background-loaded preview document, and SearchPDFCanvas presents a PDFKit view with transient search overlays and explicitly saved highlights. Explicit Open hands the selected page to the document reader. Ranking uses FTS5/BM25 candidates with a small bounded proximity preference. PDF covers are generated asynchronously with a 64-image cache; Markdown has an authored native cover and rich local HTML/MathML preview. Page overlays and DOM marks provide transient search highlights. The shared AssistantPanel uses the system on-device Foundation Models runtime on macOS 26+, with bounded retrieved passages, source references and response invalidation; no separately packaged model is required. LibraryManager owns the concise folder/index controls. No-hit spelling suggestions use FTS5 vocabulary and bounded edit distance; Explore uses a validated on-device query plan, vocabulary-grounded retries and reciprocal-rank fusion, retaining actual match terms for highlights. The independent Assistant module centralises on-device readiness, generation, evidence and panel presentation. PDFHighlightStore adds coordinated source-checked markup transactions and one-step Undo, using the fixed Okabe–Ito palette. Broader ranking evaluation and dense semantic retrieval remain subsequent work.


The PDF reader now connects that same AssistantPanel through an asynchronous passage provider. PDFAssistantContext isolates its own on-demand PDFDocument, ranks question-related page text, prioritises an owned selection/current page and returns only value-type locations and bounded passages. It neither shares the live PDFView document across actors nor depends on LibraryIndex. PDFWorkspace navigates citation locations in its own PDFSession, supplies current committed bytes and clears the document-scoped conversation when file/content changes. The shared DocumentAssistant retains per-turn source identities, bounded recent history and cancellation generations. It accepts explicitly qualified general-context replies while validating all numeric source references; citation validation is not entailment verification. No cloud provider or persistent inference session is introduced.


Ask response detail is a shared persisted Low/Mid/High preference, defaulting to Mid. It changes the next request's instruction and maximum response tokens, without creating a second model or changing evidence limits. AssistantCitation carries a caller-owned location, the original supplied excerpt and a per-click identity. It resolves contiguous normalised text ranges independently of PDFKit. PDFCitation translates those ranges into page selections; the reader's dedicated PDFCitationHighlights and Search's existing overlays paint transient focus marks, while the Markdown preview scopes DOM marks to the referenced heading section. Source disclosures start collapsed and retain per-turn evidence. Citation focus does not write annotations or mark a document dirty, and a missing PDF passage produces a short status rather than a fabricated keyword match.

## Destination-aware file drops

Convert, Compress and Combine consume their own file drops. Convert preloads images, Word or Markdown into its queue; Compress preloads one PDF; Combine accepts at least two PDFs and reviews their dropped order before choosing a new output. Card validation errors stay attached to the chosen operation instead of falling through to document opening. The rest of the main workspace opens one dropped PDF, Markdown or plain-text file through ReadingSession, preserving dirty-document guards. Recent rows provide native URL drag items, and card borders give a brief Reduce Motion-aware target indication. Background multi-file drops and unsupported card inputs show a clear error.
